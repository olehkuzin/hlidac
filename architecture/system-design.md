## 1. How it answers the brief

| `praha-03` asks for | Our product |
|---|---|
| Regularly send the patient a short side-effect questionnaire | Check-ins (started from the demo panel in this version; scheduling later) against the patient's **FHIR `Questionnaire`**, in **our own accessible, mobile-first web app** (Czech), announced in the app and by email. The patient answers in their own words, by voice or with large buttons; the app asks only the items still missing. |
| Advise the patient how to cope | Versioned, clinician-approved Czech advice cards in plain language, chosen by explicit rules. Doctor recommendations are an open point (D15). |
| Alert the care team on its own at warning levels | A deterministic rules engine over validated findings, **provisional CTCAE grades** and the patient's real treatment context from IRIS. Urgent cases alert at once (clinician app plus email), with ownership, an acknowledgement deadline, delivery tracking and fallback. Clinicians confirm the CTCAE grade. |

**Why this beats "another ePRO app"** (evidence in `../docs/deep-dive-praha-03.md` §2):
- It's built first for **patients with disabilities**.
- **Patient records never reach a model or a messenger:** the extraction model sees only the pseudonymised message text, voice is transcribed locally, and one setting moves extraction to a local model.
- It works on **the hospital's own data in IRIS**.
- Clinicians get standard CTCAE severity with the evidence behind it.
- There are fewer, explained alerts, and every alert closes a loop.

## 2. Why this wins the InterSystems prize

The prize rewards "AI, interoperability, or both". This design does both, on real hospital data in IRIS:
- **AI:** LLM extraction (the team's Azure OpenAI deployment in the demo, a local model by one setting) and local voice transcription, inside guards that leave every decision to deterministic rules.
- **Interoperability:** the template is a standard **FHIR `Questionnaire`**, and each check-in becomes a **`QuestionnaireResponse`**, with CTCAE grade `Observation`s, `Provenance` and an alert `Task`. All of it sits next to the hospital's own `Patient` and medication data in the same FHIR repository. An **IRIS Interoperability production** delivers every FHIR write and every email from our outbox, with retries and a trace.
- **One visible story:** a patient's report → the decision in the app at once → the outbox rows in the Visual Trace → FHIR write-back → the nurse's email → no acknowledgement → the escalation email.

| Criterion | What we show |
|---|---|
| Innovation | A conversational, accessibility-first ePRO on a standard Questionnaire; the LLM reads and the rules decide; provisional CTCAE grades with evidence, confirmed by a clinician |
| Real-world impact | Fewer ER visits and better quality of life (STAR, PRO-TECT); includes patients digital health often excludes; runs on the hospital's own data, and records never leave IRIS |
| Use of InterSystems technology | FHIR R4 repository with `Questionnaire`/`QuestionnaireResponse` next to real hospital data; an IRIS interoperability production (`Hlidac.Production`, IRIS classes, no IoP; D40) as the only FHIR writer; IRIS SQL for check-ins, assessments, alerts, the outbox and the audit |
| Technical coherence | One app that decides, one production that delivers, one outbox contract between them; strict Pydantic boundaries; one pure grading and rules engine called by both the app and the tests; provenance and audit end to end; a proven security posture (§9) |

**How a report flows:**
1. The patient answers in the app by text or buttons; voice is transcribed inside the app. The check-in is saved after every answer.
2. The app extracts (through the gateway), grades and assesses with pure functions, and **shows the result at once**: the urgent screen, the next question, advice, or "the team will review". An urgent assessment creates the alert row first, so the nurse queue shows it at once.
3. The app then enqueues outbox jobs: one FHIR transaction bundle (the `QuestionnaireResponse`, grade `Observation`s, `Provenance`, `Task`) and the emails, each with an idempotency key.
4. The production takes pending FHIR rows, posts each bundle to the FHIR repository and marks the row `done`; the app's outbox runner sends the email rows the same way (D40); on errors it retries and finally marks the row `failed`, which shows in Unresolved.
5. Clinician actions (acknowledge, confirm a grade, resolve) update our SQL rows at once and enqueue the matching FHIR updates. A confirmation or correction is a new `grade_review` row; the engine's provisional grade stays in its assessment.

**The outbox contract** (`src/hlidac/schemas/outbox.py`, table `Hlidac.outbox`):
- **Jobs:** `fhir_transaction` (a FHIR R4 transaction `Bundle`, posted as is) or `email` (recipient, approved template id and version, subject, plain-text and HTML body, all rendered by the app; no clinical content).
- **Checked by `src/hlidac/fhir_guard.py`** (standard library only) when the app enqueues a bundle, **and again by the production just before posting**:
  - only our five resource types, each carrying the `hlidac` tag;
  - every write is a conditional PUT (or a POST with `ifNoneExist`) on exactly one identifier, which must be the resource's own identifier in one of our systems (`urn:hlidac:…`); `Provenance`, which has no identifier in R4, is written by PUT on our own id (`hlidac-…`). So a write can never match a hospital resource, and a retry never duplicates;
  - never DELETE or PATCH;
  - the bundle is stored as a JSON string, so it can't change after the check.
- **Processing:** pending rows in `created_at` order; success → `done` + `processed_at`; error → `attempts` + 1 and `last_error`; after `MAX_ATTEMPTS` (5) → `failed`. The production updates only the status columns, never the job.
- **Idempotency:** enqueueing an existing `idempotency_key` is a no-op.
- **Who processes what (D40, D43):** the production processes `fhir_transaction` rows; the app's runner (`OUTBOX_RUNNER=app`) sends `email` rows and redacts login codes.

**Rules for the build:**
- **Domain logic is pure Python** with no IRIS imports: schemas, extraction validation, CTCAE grading, assessment, clarification, advice selection, FHIR mapping. The production imports only `fhir_guard.py` and moves ready jobs.
- **The frontend is server-rendered HTML with progressive enhancement** (FastAPI + Jinja2 + plain CSS + one small JS file for voice), following `accessibility.md`. Czech only (`lang="cs"`).
- **Models are called only through the model gateway** (D5). Voice: `mlx-whisper` inside the app on the demo Mac. Text: the team's Azure OpenAI deployment or a local Ollama, chosen in config, both through the `openai` SDK; the gateway pseudonymises text before a non-local call and never sends records.
- **Content is versioned files in git** (`data/`): the Questionnaire, CTCAE mappings, rules, advice cards and templates. Every assessment records the versions it used (D12).
- **The hospital data is read-only for us.** Everything we write carries the FHIR tag `urn:hlidac:tag|hlidac` or lives in the SQL schema `Hlidac`, so it can be found and removed without touching the original records.
- **Urgent action never waits:**
  - the urgent screen and the alert row exist before any outbox job runs;
  - email is a mirror and never the only path;
  - every outbox job is idempotent.
- **Without IRIS,** the app runs on `InMemoryStore` and `StaticContextSource` (hand-made fixtures, no patient data) through the same code paths.

## 5. Data contracts (Pydantic, `src/hlidac/schemas/`, WP0)

Every model derives from `Strict` (`extra="forbid"`, `strict=True`, `frozen=True`). A validation failure leads to a bounded retry, a targeted clarification, or a visible processing error. It never becomes a successful completion. **These schemas are the shared contract between work packages; change them only together with their tests (`tests/test_schemas.py`), and tell the team.** The validators enforce the principles, not just the types. To change a record, use `record.evolve(...)`, which validates again; `model_copy(update=...)` skips the validators.

| Schema | Key fields and enforced rules |
|---|---|
| `InboundMessage`, `ButtonAnswer` | `message_id`, `checkin_id`, `patient_id`, `session_account_id`, **`reported_by`** (`patient`/`caregiver`), `received_at`, `kind` (`text`/`voice`/`answer`) with exactly its own payload: `text`, `audio_ref` or `answer` (`link_id` + option code, including `dont_know`) |
| `Transcript` | `message_id`, `text`, `model`, `model_version`, `confidence`; `review` (`pending`/`confirmed`/`corrected`/`rejected`) and `corrected_text` |
| `Finding` | **`link_id`**, **`state`: `present` / `absent` / `not_mentioned` / `unknown`**, `value` (`Quantity`: value + UCUM unit), `code`, `attributes`, `onset_text`, **`source`** (`QuoteSource`: message + verbatim quote, or `AnswerSource`: the button answer), `extractor_version`, `confirmed`. `not_mentioned` carries nothing; every other state needs a source; "Nevím" always means `unknown`; a quoted finding records the extractor version |
| `ExtractionResult` | `findings` (at most one per item), `contradictions`, `uncertainties` |
| `CtcaeGrade` | `ctcae_term`, `ctcae_version`, **`grade`** (1–5) or **`at_least`** + `needs_clinical_assessment`, `basis`, `mapping_id` + `mapping_version`, **`status`: `provisional` / `confirmed` / `corrected`**, `confirmed_by`, `confirmed_at`. A provisional grade has no reviewer; a reviewed grade names the clinician and is exact |
| `MonitoringPlan`, `PlanItem` | From the FHIR `Questionnaire`: url, version, items (`link_id`, type `choice`/`quantity`/`text`, `required`, `red_flag`, CTCAE term, approved Czech text, answer options, `enable_when`) + rule, mapping and advice-card ids, `max_clarification_turns`, `source_ref`, approver. **Every choice item offers "Nevím"; red-flag items are choice items** (G3) |
| `PatientPlan`, `AccessibilityProfile` | Hospital patient id, Questionnaire url\|version, care team, **accessibility** (text size, contrast, screen reader, voice-first, simplified), approver, `active_from` |
| `PatientContext` | Last SACT dose, regimen, baseline grades, `source_refs` (the FHIR references read), `read_at`. Read only; feeds the rules, never a model |
| `Checkin` | Messages, transcripts, the merged findings, `pending_link_id`, `clarification_turns`, `status` (`in_progress`/`completed`/`processing_failed` with its `failure`); saved after every answer |
| `Assessment`, `TriggeredRule` | **`status`: `urgent` / `routine_review` / `insufficient_information` / `no_escalation`**, **snapshots of the findings and the `PatientContext` the engine saw** (for replay), provisional grades, triggered rules (id, version, inputs, reason), missing items, advice card id + version, Questionnaire, ruleset, mapping and engine versions, `assessed_at`. **An urgent rule makes it urgent; `no_escalation` is impossible with missing items, an escalating rule or a grade that needs clinical assessment; advice only follows `no_escalation`** |
| `GradeReview` | A clinician's confirmation or correction (the reviewed `CtcaeGrade`, plus a reason for a correction); append-only, separate from the assessment |
| `AdviceCard`, `CardCondition` | Id, version, Czech text + easy-read version, follow-up, conditions (item + grades), exclusions, required items, `source_url`, approver, review date |
| `Alert` | Owner team, priority, `ack_deadline`, `status` (`open`/`acknowledged`/`resolved`) with exactly the matching who and when, resolution note, `fallback_level` |
| `Notification`, `Delivery` | Recipient, kind, approved template id + version, `link` (an app path with no query string), deliveries (in app; email points to its outbox row); **no clinical content in the email** |
| `Account`, `LoginCode` | A patient account is bound to one patient, a nurse account to a team; emails lower-case; only the hash of a login code is stored |
| `AuditEntry`, `ModelCall` | Who, what, target, details; a model call keeps exactly the text sent (after masking); transcription is always local |
| `OutboxItem`, `FhirTransactionJob`, `EmailJob` | The outbox contract (§3) |

Medication-use reporting (spec §5) and caregiver accounts get their own schemas when they're built.

**The persistence seam** (`src/hlidac/store.py`): the app talks only to `Store` (accounts, login codes, plans, check-ins, assessments, alerts, notifications, outbox, audit) and `ContextSource` (hospital treatment context, read only). `InMemoryStore` and `StaticContextSource` run everything without IRIS; the IRIS versions implement the same methods (WP10, WP14). Assessments and the audit log are append-only.

**Finding states in the UI and in FHIR:**

| State | Meaning | Comes from | In the `QuestionnaireResponse` |
|---|---|---|---|
| `present` | Reported | quote or button | the answer (the quote stays in our SQL record) |
| `absent` | Explicitly denied | quote or "Ne" button | "Ne" |
| `not_mentioned` | Not talked about or skipped | — | no answer |
| `unknown` | Asked, and the patient doesn't know | **"Nevím" button** or a quote | "Nevím" |

Only `absent` can close a red-flag item.

## 6. Grading and assessment: the LLM reads, the rules decide

**Order** (from the diagram, plus grading), each step a pure function:
1. **Grade:** `grade(findings, mapping, context) -> list[CtcaeGrade]`, provisional.
   - Only the approved mapping is used; never the LLM.
   - A missing attribute gives `at_least` + `needs_clinical_assessment`, never a lower grade.
   - Criteria that aren't patient-reportable are never guessed.
2. **Urgent rule met?** Evaluated on the available validated data at once. If yes → `urgent`: urgent screen, team alert, and routine questioning stops.
3. **Enough information?** A required item, or an attribute needed for grading, is missing → the next approved item. After the maximum number of turns → `insufficient_information`, visible in Unresolved.
4. **Routine review required?** → `routine_review`, the nurse queue, and an approved "the team will review" message.
5. **Otherwise, select an eligible card.** A match sends the advice; no match follows the plan's policy. "No alert" alone never selects advice.

**Demo default rules** (sourced, labelled "DEMO", need Motol approval; WP2 transcribes the per-symptom definitions):

|---|---|---|---|
| Fever in treatment context | Temperature ≥ 37.5 °C or < 36.0 °C, or "generally unwell", **and** last SACT dose ≤ 56 days ago or immunocompromised (from the hospital record). Our conservative addition: reported fever without a measured number counts too. Chills alone are **not** in this UKONS rule (corrected Fri 16 Oct); chills stay a red-flag question | urgent | UKONS v3, row "5. Fever on SACT" ("Within the last 6-8 weeks or immunocompromised"), p. 10 |

**How an LLM error is contained** (each item is testable):

| # | Guard |
|---|---|
| G1 | **Schema-bound output:** strict JSON-schema structured output, temperature 0, a fixed seed and a pinned model (Azure deployment version or local model digest). Invalid output → bounded retry → visible failure. |
| G2 | **Quote check:** every `present`/`absent` finding from free text carries a verbatim quote, or it is dropped. |
| G3 | **Red-flag items are asked with buttons** when `not_mentioned` or `unknown`. |
| G4 | **Deterministic red-flag phrase scan** (**P0**, D43): a hit can only raise urgency. |
| G5 | **Consequential values** (temperature, dose, voice transcripts) are confirmed before they can *close* an item; they can always *raise* urgency (a value the model read from the patient's words raises it once confirmed with one button or once the report is sent, D49). A value the patient corrects or rejects is dropped, and the item is asked again with buttons. |
| G6 | **Model gateway:** `PATIENT` text goes only to allow-listed endpoints (local or the approved Azure deployment) and audio only to local Whisper; anything else raises. Before a non-local call the text is pseudonymised (the patient's name, birth numbers, phone numbers, email, street addresses), and no request carries records, identifiers or treatment context. Exact inputs (as sent) and outputs are logged in the audit (inside IRIS). |
| G7 | **Evaluation set:** labelled test reports written by the team, run against real patient contexts locally, on both model backends (Azure and local); target 0 missed urgent. Results go into git as aggregates only. |
| G8 | **Grades come only from the mapping;** provisional until a clinician confirms; never shown to the patient. |

## 7. FHIR R4 mapping

The kit server is R4 (`hl7.fhir.r4.core@4.0.1`). IRIS validates each write and returns an `OperationOutcome` on errors. Every resource we write carries `meta.tag` `urn:hlidac:tag|hlidac` and an identifier in our own system (for example `urn:hlidac:checkin|<id>`), and is written by a conditional PUT on that identifier, so retries never duplicate. `Provenance` has no identifier in R4, so it gets our own id (`hlidac-…`) and is written by PUT on it. `fhir_guard.py` enforces all of this (§3).

| Record | Resource | Notes |
|---|---|---|
| Patient, treatment context | Hospital data: `Patient`, `MedicationRequest`, `MedicationAdministration`, lab `Observation`s … | **Read-only for us.** WP14 reads the last dose from `MedicationAdministration` or the anticancer-therapy `Procedure` (D43). |
| Monitoring template | **`Questionnaire`** | `url` + `version`; items with our symptom code + CTCAE term in `item.code`; `answerOption` including "Nevím"; conditional items via `enableWhen` |
| Check-in | **`QuestionnaireResponse`** | `questionnaire` = canonical url\|version; `status` `in-progress` (partial) → `completed` (or `amended` after clarification); `author`/`source` = the Patient; free-text and transcribed answers as `valueString` |
| CTCAE grade | `Observation` | `code` = CTCAE term (coding system to confirm with the mentors); `valueInteger` = grade ("at least" grades say so in `note`); `status` `preliminary` → `final` on clinician confirmation; `derivedFrom` → the `QuestionnaireResponse`; `method` = mapping version |
| Source of a grade | `Provenance` | id `hlidac-…`; target = the grade `Observation`; entity = the `QuestionnaireResponse`; agent = our engine and extractor versions. Each finding's quote or button answer stays in the check-in record (SQL) |
| Alert | `Task` | `priority` `stat`/`routine`; `owner` = the team; `restriction.period.end` = acknowledgement deadline; `focus` = the `QuestionnaireResponse`; `status` `requested` → `accepted` → `completed`; grouped episodes reuse the open Task |

Not in FHIR in this version: notifications and the audit trail (SQL `notification` and `audit_log`; `Communication` and `AuditEvent` later), medication use (`MedicationStatement` later), caregivers (`RelatedPerson` later).

## 8. IRIS SQL (schema `Hlidac`)

- **Tables** (`src/hlidac/iris/schema.sql`): `account`, `login_code`, `patient_plan`, `checkin`, `assessment` (append-only, replayable), `grade_review` (append-only), `alert`, `notification`, `outbox`, `audit_log` (append-only, including exactly what each model saw).
- **Each row** keeps the full Pydantic record as JSON (`record_json`) plus the columns needed for lookups. In `outbox`, the status columns are the truth and `job_json` holds only the job, so the production updates columns and never rewrites JSON.
- **Content is not in SQL:** the Questionnaire, CTCAE mappings, rules, advice cards and templates are versioned files in git (D12), labelled "DEMO — čeká na schválení FN Motol" until approved; assessments record which versions they used.
- **Rules:**
  - CE allows 8 connections, so the app uses one shared connection;
  - **the app uses a least-privilege IRIS account**, not `SuperUser`;
  - timestamps in columns are UTC.

## 9. Security: how we prove it

| Threat | Control | Proof (test or demo) |
|---|---|---|
| Patient data leaves the hospital (third parties, cloud AI) | Own web app; local Whisper; the model gateway's endpoint allow-list, pseudonymisation and minimisation (no records to the model); emails without clinical content | Gateway guard tests (a non-allow-listed endpoint raises, audio to a non-local endpoint raises, masked identifiers are absent from the text sent); email-content test; architecture slide |
| Someone reads another patient's data | Session bound to one patient (or caregiver); every query scoped by patient; role checks for staff | Authorisation tests: patient A → B's report = 403; staff without a role = 403 |
| Account takeover | Passwordless single-use email codes (hashed), short expiry, rate-limited; secure session cookies (Secure, HttpOnly, SameSite=Strict), rotation on login | Auth tests (expired or reused code rejected) |
| Cross-site attacks | CSRF tokens on every form; strict CSP (no inline script), X-Content-Type-Options, frame-ancestors none, Referrer-Policy | Header tests + a CSRF test |
| Interception | The demo runs at `localhost` on the laptop; IRIS is reached only through an SSH tunnel; HTTPS + HSTS once deployed | Tunnel and closed ports shown; deployment is future work |
| Malicious upload | Audio only: type, size and decoding checks; never served back as-is | Upload tests |
| Leaks through logs, URLs, git or agents | No patient data in URLs or application logs (audit inside IRIS only); `.gitignore` and review rules; agents never read patient records (`AGENTS.md`) | Log check; repo review |
| Unnoticed misuse | SQL `audit_log` for every access and action, including model calls; audit screen | Audit trail shown in the demo |
| Over-privileged database access | Least-privilege IRIS user for the app; hospital data read-only for us | IRIS role configuration shown |

We claim no certification or penetration test. The pitch states exactly what is tested.
